# Reflection feasibility after the rejected smoothness comparison

2026-09-08. **Recommend one isolated prototype of Unity's existing preview SSR on the pinned URP 17.6 package, beginning with an explicit compile/resource/pass availability gate.** It is not enabled in the current native player. This is feasibility work only: no define, dependency, renderer, shader or runtime implementation was changed, and no build or game was launched for this report. The parent owns restoration of the accepted control.

## Evidence and decision boundary

[The prior A/B/C review](../environment-reviews/021-stage1-lighting-road-native.md), [lighting-road decisions](../../evidence/night-production/lighting-road/decision.md) and [handoff](../HANDOFF.md) preserve the evidence: reflection-enabled B darkened the road without useful broad reflection shape; D's two local 256 px box-projected probes completed but did not establish the required benefit. The parent and independent reviewer now reject smoothness candidate 01, GUID `1441c9f070434c73a2c65dd244581929`, for insufficient full-frame improvement. It shifted mask .35–.50 to .45–.60 with multiplier .90; this changed direct-highlight shape, not the available reflected scene information. No catastrophic regression was reported. Preserve [candidate evidence](../../evidence/night-production/road-response/candidate-01/) and [control evidence](../../evidence/night-production/road-response/control/) separately.

| Technique | What it supplies | Fit to this road | Decision |
| --- | --- | --- | --- |
| Existing cubemap/probes | Captured surroundings, including offscreen objects; roughness-filtered sampling. Box projection approximates finite enclosure parallax. | One box cannot represent the depths of curved nearby rails, overhead lamps and distant towers simultaneously. Current satin roughness blurs thin sources heavily. | Keep the readable control; another arbitrary intensity/resolution increase has no demonstrated basis. |
| Native preview SSR | Reflection rays against the current view's depth and colour, using per-pixel surface normals. | Naturally follows road banking/curvature. Can reflect visible broad architecture/emission with spatial correspondence; cannot supply offscreen/occluded sources. | Smallest justified next technique, conditional on actual native availability and visual gain. |
| Planar reflection | Another camera mirrored about one plane, rendering offscreen scene information. | Exact only for a planar surface. The course has changing height and bank; one plane produces sliding/misaligned reflections. | Do not choose for the whole running deck. A local flat patch would be a different, limited receiver experiment. |

Unity's [box-projection explanation](https://docs.unity3d.com/6000.0/Documentation/Manual/AdvancedRefProbe.html) describes finite cubemap walls, not actual scene intersections. The fit judgment above follows from that model and the project's changing [TrackPath frames](../../UnityProject/Assets/Scripts/World/TrackPath.cs). D used initialization captures; its cost must not be described as six extra scene renders every gameplay frame. Updating probes every frame would be a new, unmeasured technique.

- [Global settings](../../UnityProject/Assets/UniversalRenderPipelineGlobalSettings.asset) already contains `ScreenSpaceReflectionPersistentResources`, referencing ComputeScreenSpaceReflection and BlitFullPrecision shaders. Resource presence alone is insufficient: the feature's preparation code requires them at runtime, and the SSR settings stripper preserves them when an active SSR feature is serialized in a renderer included in the build.

Unity's [official preview announcement](https://discussions.unity.com/t/preview-of-screen-space-reflections-for-urp/1721494) identifies this as preview work targeting 6.7, available to try from 6000.6 alpha. Its linked guide did not expose readable contents through the browser used for this audit. A separate [official issue reproduction](https://issuetracker.unity.com/issues/24156/ssr-all-gameobjects-keep-rendering-black-after-restoring-a-valid-transform-scale-when-screen-space-reflections-is-enabled) explicitly identifies the Player scripting symbol `URP_SCREEN_SPACE_REFLECTION` as the enablement step for earlier 6000.6–6000.7 versions. Thus there is a documented opt-in route; there is **no evidence yet that this project's native SSR builds or renders correctly**. No package upgrade or third-party dependency is justified before checking that route.

## Integration constraints from the pinned source

`ScreenSpaceReflectionPass.Setup` supports the forward path, requests Depth + Normal and sets `writesSmoothnessToDepthNormalsAlpha`. The default before-opaque mode also requests motion vectors for game cameras and reads previous-frame colour/depth for reprojection. RenderGraph owns the pass and its temporary textures; the local `RenderGraphSettings` marks the old compatibility switch obsolete and returns false. Do not copy an old compatibility-mode implementation or switch to Deferred as a supposed requirement.

SSR intermediates explicitly use one sample/no MSAA. There is no source-level rejection of camera MSAA 4 in the inspected setup; this is not proof of artifact-free Metal resolves. Existing SSAO already requests depth/normals, but added smoothness output, history, reflection buffers, marching, filtering and bandwidth remain additional work. Their cost is unmeasured.

The road is standard Lit with `_NORMALMAP`, `_METALLICSPECGLOSSMAP`, direct specular and `.90 × mask-alpha` retained. Lit's DepthNormals pass supports smoothness output. `ShaderLibrary/GlobalIllumination.hlsl` samples SSR separately from `_ENVIRONMENTREFLECTIONS_OFF`; keeping cubemap sampling off does not itself disable SSR. Its separate opt-out is `_SCREENSPACEREFLECTIONS_OFF`. This permits a comparison retaining the control's cubemap state. Missed SSR rays would retain the existing fallback contribution, not magically reveal a probe that the material disables.

[NightWindows](../../UnityProject/Assets/Shaders/NightWindows.shader) is opaque and borrows Lit DepthOnly/DepthNormals passes; its visible emitted colour is a potential reflected source. It uses custom lighting, so receiving SSR on those facades is not automatically established. Borrowed pass/material layout and source depth must be checked natively. [IonTrail](../../UnityProject/Assets/Shaders/IonTrail.shader) is transparent without those depth passes: opaque-only SSR should not be advertised as reflecting the plume. The initial test should avoid transparency support and extra transparent prepasses.

The official issue above reports persistent black output after a zero-scale transform in preview SSR. This audit has not reproduced that fault or shown this course triggers it. It establishes preview risk and a concrete reason to inspect nonfinite/black propagation over motion; it does not establish a bug in the current control.

## One bounded prototype, if subsequently authorized

Use the existing package's **before-opaque, opaque-only SSR**, retaining the control road, fog, lights, camera, geometry and race settings. First add only the documented standalone scripting define in an isolated prototype revision; verify compilation, actual feature/volume types and native resource availability. Serialize one active feature into the selected renderer and add one volume override. A compile failure, missing resource or absent SSR pass is an availability failure: preserve it and stop, rather than silently upgrading packages or substituting another technique.

One starting configuration follows the local Balanced marching preset: Half resolution, Bilinear upscaling, Linear marching, 32 steps, 30 m ray length, 5 refinement steps, object thickness .325, final thickness multiplier .05. Keep Gaussian roughness filtering, roughness scale 0, strength 1, minimum smoothness .05, fade start .1, sky reflection off and temporal filtering off. The default before-opaque path still requires reprojection history even with temporal filtering off. This is one explicit diagnostic configuration, not an optimized shipping preset. The 30 m limit specifically tests nearby structure; a miss beyond that distance cannot reject all SSR implementations.

Record native feature/type/volume settings, shader/resource identities, depth/normal/smoothness availability, and the actual SSR pass. Compare the opening-city passage with SSR disabled/enabled using the same build and settings; preserve natural camera/progress differences. Require a clear whole-frame road benefit tied to an existing visible source, preserved dark aggregate/edge readability and stable banking response. Inspect source screen-edge disappearance, craft occlusion, turns, disocclusion/history trails and bright-source clipping in continuous motion. Do not add an unrequested smoothness retune to make the effect appear successful. If the only gain is a magnified crop or a fragile mirror patch, retain the control.

A planar fallback is not part of this prototype. It would require a reflected camera/view/projection, oblique clipping, reversed culling with guaranteed restoration, recursion exclusion, target lifecycle and a custom road sampling/compositing path. Unity supports a [single-camera render request](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Rendering.RenderPipeline.SubmitRenderRequest.html), but that API is not a built-in URP planar-road material. A moving tangent plane would match only one neighbourhood; multiple planes introduce additional renders and transition seams. None of that is a smaller experiment than testing the existing SSR feature.

## Performance gate

No SSR or planar GPU time, memory increase or frame-rate estimate is claimed. If the visual prototype passes, run separate native real-time control/effect/control samples on the same M2 Max, resolution, display/VSync and route, after warm-up and without concurrent build/bake/encoding. Keep simulation-time recording disabled. Record observed mean/P95/P99 intervals, memory and hitch counts; use Unity/Xcode GPU timing if available to separate SSR passes from display waiting. Preserve any bad sample and repeat only to resolve a concrete anomaly. Compare against the restored control, not an old build's numbers. Advancement requires a worthwhile visual gain and no material regression against the agreed frame budget; until measured, performance remains open.
