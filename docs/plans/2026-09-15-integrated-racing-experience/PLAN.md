# Vector Rush：完整赛车体验重制计划

2026-09-15。状态：规划与四份分工交接完成，由用户在新任务下达实施指令。本轮只修改计划与交接文档。

## 目标

建立统一、鲜明的赛博朋克反重力赛车体验：密集而多样的城市包围赛道，平顺的弯道带来侧倾和速度感，霓虹影响周围材质，飞船在加速与碰撞时有饱满、快速、分层的反馈，字体与 UI 动效属于同一种赛车风格。

第一项成品交付是约 30 秒、可实际驾驶的完整示范段，涵盖常速进入、加速、boost、倾斜弯道、释放与恢复。碰撞若不能自然出现在该次驾驶里，另交一段明确标注的真实接触演示，不强行制造主片里的事故。它是全游戏品质标准的验证样本，不是把最终目标缩小成一个漂亮镜头。

## 根因与制作原则

1. **统一美术语言不足。** 先定义建筑轮廓、材质、霓虹、飞船、字体和运动的共同规则，再制作内容。
2. **资产种类、构造与布局不足。** 给弱资产明确的保留、改造、替换或降为远景的结论，不能默认现有楼只需更多窗户。
3. **静态截图主导迭代。** 用正常镜头的连续驾驶判断画面，静帧用于诊断，不能独立通过验收。
4. **事件反馈缺少共同节奏。** 加速、boost、擦墙、重撞、排名变化由现有真实事件驱动，统一起势、峰值和消退。
5. **技术完成取代品质判断。** 构建、测试和性能是交付门槛；全画面是否明显达到目标是另一项必须通过的判断。

本轮改变呈现层的基础。保留可复用的游戏逻辑与可靠工具，不增加赛道数量、道具、护盾玩法、变形能力、成长系统或其他玩法。已有声音表现纳入整体同步与混音，避免另开音频功能工程。

## 当前起点与事实边界

- 当前观测源码提交为 `7358f77`，在 `b987c23` 蓝色粒子尾焰基础上加入开场道路灯光候选。实施时重新确认 HEAD、工作树、运行项目与 app 身份。
- 道路候选提供直接光照，不等于建筑或车辆反射；旧 probe/SSR 配置没有证明足够视觉收益。
- 用户认为蓝色尾焰候选过细，缺少体积、喷射速度与粒子冲击力。它是保留对照，不是冻结的美术标准。
- 源码已有连续样条、按弯曲计算的倾斜（当前限制 ±17°）、镜头跟随/FOV/抖动、碰撞粒子、Bloom、UI 排名/boost 提示和分层声音。不能把“效果不够”误写成“系统不存在”。当前初始化未见 MotionBlur 配置，仍须核对实际运行 Volume。
- 参考视频可见实体飞船切到青白轮廓/半透明状态，并显示 HOLOGRAPHIC PHASE。具体触发与实现未知。把船身变化作为现有 boost 的表现设计方向，不复制一个新玩法。
- 当前建筑多样性、稀疏度与 prototype 感来自用户反馈和已查看的原生画面；全资产库尚未完成质量审计。正式资产清单应来自下一阶段的实物检查。

## 美术方向

采用“高密度垂直城市中的霓虹竞速通道”。保留反重力赛车、夜城和蓝色推进身份。

- **结构：** 近处有可信的厚度、支撑与连接；中景有明显不同的建筑体量；远景形成相互遮挡的高低天际线。
- **色彩：** 冷色城市空气；青蓝导向灯与推进器；局部洋红标识；暖色窗灯与碰撞火花。让颜色有用途与主次，避免所有物体同亮。
- **光：** 可辨认的亮芯、局部彩色光晕、邻近表面响应。亮处仍保留形状；城市暗部不是空洞。
- **细节：** 把预算放在驾驶距离内看得见的轮廓、立面分区、招牌、护栏节奏与近景掠过物；远楼不要求每扇窗都清晰。
- **动态：** 建筑本体保持稳定；少量屏幕内容、低频灯光变化及不参与碰撞的远景交通光点提供活跃感。车速感主要来自真实视差、镜头响应、有限模糊与事件反馈的配合。

## 制作阶段

### 阶段 0：确定成品标准与资产取舍

在原生游戏内选出一段连续路线，记录入口、弯道、出口的路线进度和正常镜头。看完整参考视频与当前同长度驾驶片；整理一张对照板、三张构图草图和一张保留/改造/替换清单。

对照板必须覆盖城市、赛道/护栏、霓虹/雾、飞船/推进、速度/碰撞、字体/UI。生成图只能帮助表达方向；短视频中的运动与原生效果才决定采用与否。规划产物保持短小，完成后进入场景制作，不再派生一轮长报告。

### 阶段 1：完成同一段原生体验

以下是同一完整体验的制作依赖，按文末四任务分工协作，由 01 统一集成。各项尽早在一个可运行场景里汇合，不以各自通过代替整体判断。

**A. 先重建空间与资产骨架。**

按资产实物审计形成一个可复用的城市组合：建议先做 4 类可明显区分的建筑家族（宽体商业塔、瘦高住宅/酒店、退台服务楼、交通/工业设施），1 个方向明确的地标，以及裙楼、连桥、屋顶设备、招牌、护栏导向模块。数量是起始制作预算，不是完成标准。尺度、顶部、体块、立面分区都要不同，不能只调高度和换窗贴图。一个路段里安排近、中、远层次，避免沿路等距复制。

采用已有合格资产、可复现的 Blender 硬表面制作、经许可核实的外部资产组合。先用原生大形和灯光验证，再细化材质；不为未被镜头看见的微细节投入大量制作。外部资产记录来源与许可，付费采购另需明确预算，不把采购当成默认动作。

**B. 把路、城市材质、灯光和空气做成一个整体。**

校准曝光与色调映射后，统一粗糙度、灯芯、Bloom、道路受光和距离雾。优先验证现有 URP 路径可用的效果。远景逐步降低对比度并融入雾色，保留中景轮廓与城市灯点；不能用浓雾掩盖整个稀疏布局，也不能简单全屏增亮。已有道路灯光候选可重新平衡，避免船身高光泛白。需要反射时先证明源数据和接收材质有效，禁止继续无依据地扫 SSR 参数。

补齐有用途的护栏箭头、分段灯、编号/赛段标识和广告面板。指引沿真实曲线与倾斜贴合、连贯可读；广告动态的亮度与频率低于驾驶关键提示。

**C. 设计速度与飞船的完整事件响应。**

先核对当前实际倾斜、路面法线与网格过渡，再决定是否需要调整。区分路面倾斜、船身视觉侧倾和镜头滚转，避免叠加成过度倾斜。镜头跟随、前视和 boost FOV 有限幅与阻尼；近景掠过与环境流动提供持续速度感，碰撞使用短促冲量，避免一直抖。

试验受控的运动模糊，验证深度/运动矢量、透明特效和 UI 的渲染顺序。不能假定打开 URP MotionBlur 就等于参考效果；如果采用外围方向性模糊，要标明它是风格化近似，并保留中央赛道与飞船可读性。尊重已有减弱动态、镜头舒适度设置；新增效果也必须有关闭/降级路径。

飞船 boost 状态采用亮度/能量纹理、局部轮廓、短促激活与尾迹响应。先在现有模型和材质上证明明显的船身变化。碰撞体、质量、速度、操控和能力规则不随材质效果变化；机械开合只在后续资产判断确有价值时制作，不为模仿视频新增变形玩法。

尾焰重新建立饱满主体、明亮核心和外散粒子的比例，体现快速向后喷射、翻卷、分裂与消散。让点火、持续推进和释放形态不同。支持蓝色方向；禁止把“更多粒子”“更窄”或“更长”本身当作品质指标。

**D. 完成碰撞、声音、HUD 的共同反馈。**

在真实接触点按接触强度和滑动方向触发闪光、金橙细长火花与碎片状亮点。持续擦墙采用受限的持续发射，结束接触即停止；重撞有更强的短暂爆发。粒子池、冷却、远处对手降级及屏幕遮挡上限要明确。装饰碎片不新增损伤/物理玩法。声效、船身反馈和 UI 警示同步且有轻重之分。

建立一套有赛车个性的显示字形与清晰的小字搭配，限定字重、倾斜、字距、尺寸和颜色用途。先覆盖速度、排名、boost 和已有事件提示；动效对应真实事件，并明确出现、强调、保持、退出。只使用已有游戏数据，不新增护盾条或虚构指标。IMGUI 可以继续用；框架迁移必须由已证明的表现障碍推动。字体需核实许可和所需语言字符覆盖。

同步已有引擎、风声、boost、碰撞与 UI 声音的强弱和起落，不以新增音乐系统替代混音。最终片要含真实游戏声音。

### 阶段 2：整体打磨与用户评审

交付约 30 秒连续原生驾驶片、碰撞补充片、可玩 app 和当前/候选对照。技术自检期间随时修复问题，最后一次正常镜头评审必须同时检查所有维度，不允许每个子系统自称通过就直接汇总为通过。

第一道品质门槛是用户认可这段整体方向。若城市仍重复稀疏、速度仍平、尾焰仍像贴片/水柱、霓虹泛白或 UI 像通用面板，就继续解决具体根因，不扩大铺量。向用户如实说明尚未达标的项，技术完成不冒充审美接受。

### 阶段 3：扩展到整条赛道及全部既有界面

用户认可示范段后，把同一标准扩展到剩余路线，逐段设计密度、明暗、围合/开阔的节奏；复用模块语言，不复制同一排建筑。覆盖所有既有菜单、暂停、设置、结果及对应状态，补齐一致的字体、过渡和反馈。

最后检查整场比赛的性能、资源加载/回收、重复游玩、重开、暂停/恢复、设置持久化与完整 UI 操作。通过这些并取得用户整体认可，才接近结束本次呈现层重制。示范段完成不等于全游戏完成。

详细标准见 ACCEPTANCE.md。新的性能目标暂定当前 M4 Max 原生 1080p 持续 60 fps 级别，至少测整段和碰撞压力段；它是规划目标，不是现有证据。记录 CPU/GPU 的可用测量、p50/p95/p99、长帧、分辨率与画质；短暂均值不能证明持续流畅。为雾、透明过绘、模糊、额外灯光和城市资产设预算，再据实调整。
